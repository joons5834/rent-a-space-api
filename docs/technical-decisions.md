# 기술 의사결정 기록: 동시 취소 처리와 검증 범위

> 2026-10-03 기준
>
> 이 프로젝트의 MVP는 학습용이고 운영 서비스가 아닙니다. 결제와 정산은 MVP 범위에서 뺐습니다. MVP 이후에 넣을지는 아직 정하지 않았습니다.[1] 아래에 적은 락, CI, AI 리뷰 관련 결정도 모두 MVP 단계에서 내린 것입니다.

## 배경

PRD(Discussions #1)에는 MVP 기능이 정리돼 있습니다. 회원 가입, 공간 탐색, 무료 공간 예약과 취소가 들어갑니다.[1] 기술 설계 문서(Discussions #3)에는 Java, Spring, PostgreSQL, JPA(Hibernate)로 이루어진 스택과 ERD, Postman API 초안 링크가 있습니다. 기술 설계 #3에는 스택 목록이 있지만, 선정 이유는 기록되지 않았습니다. 다만, 스택 목록이 학습용 MVP에서 표준적인 선택이며 회고와 코드를 통해 선정된 스택을 필요할 때마다 재평가합니다.[2]

위와 같은 실수를 반복하지 않기 위해 이 문서는 주간 회고(Discussions #46)와 그 뒤의 코드, 이슈, PR 기록을 근거로 결정 과정을 정리합니다.[3][4] 회고에서 세운 계획과 실제로 구현하고 실행한 결과는 나눠서 적었습니다. 이 문서를 쓰면서 CI 작동 로그를 확인하였습니다.

## 1. 동시 취소는 비관적 락으로 막았습니다

### 문제

이미 취소된 예약을 다시 취소하면 HTTP 409로 거부되도록 처리되어 있었습니다. 처음에는 예외 매핑이 빠진 것으로 짐작했지만, 2주 차 회고에서 다시 보니 그게 원인이 아니었습니다. 같은 예약에 취소 요청이 동시에 들어오면 둘 다 통과했던 것입니다.[3]

MVP에는 결제가 없으니 환불이 두 번 나가는 일은 생기지 않습니다. 여기서 막아야 하는 건 한 예약의 상태가 '취소'로 두 번 바뀌는 상황입니다.[1][3]

### 검토한 방법

- **비관적 락:** 예약 행을 잠근 뒤 상태를 확인하고 바꿉니다. 앞선 작업(#11, #35)에서 쓴 방식과 같고, 스키마를 고치지 않아도 됩니다.
- **낙관적 락:** `@Version` 컬럼을 추가하고 충돌이 나면 따로 처리해야 합니다. 당시에는 SQL 스키마를 손으로 관리하고 있었기 때문에 컬럼 하나를 더하는 일도 부담이었습니다.
- **조건부 UPDATE:** 바뀐 행의 수를 보고 성공 여부를 판단합니다. `@Modifying`과 영속성 컨텍스트 정리 설정을 함께 챙겨야 한다는 점을 비용으로 봤습니다. 다만 `clearAutomatically=true`를 모든 조건부 UPDATE에 꼭 붙여야 하는 것은 아닙니다.

비관적 락을 고른 건 기존 코드와 방식을 맞출 수 있고 스키마를 바꾸지 않아도 됐기 때문입니다. 세 방법의 성능을 재 보고 결정한 것은 아닙니다.[3]

### 적용과 결과

`ReservationRepository.findByIdForUpdate`에 `PESSIMISTIC_WRITE`를 걸고, `cancelReservation`이 이 메서드로 예약을 읽어 오도록 바꿨습니다.[3][4]

- 같은 예약을 취소하는 작업 10개를 한 번에 동시에 실행했습니다. 수정 전에는 10개가 모두 성공했습니다(`succeeded=10, rejected=0`). 성공은 1건이어야 하니 테스트는 실패했습니다.[3]
- 수정 후에는 1건만 성공하고 9건이 거부됐습니다(`succeeded=1, rejected=9, unexpected=0`). 테스트와 main 빌드 모두 통과했습니다.[3]
- 여기서 10이라는 숫자는 한 번의 실행 안에서 동시에 돌린 작업 수입니다. 테스트를 10번 반복했다는 뜻이 아닙니다.
- 이 테스트는 HTTP가 아니라 서비스 메서드를 직접 호출합니다. 그래서 동시 HTTP 요청 9건이 409를 받았다고까지는 말할 수 없습니다. 409 응답은 순차 재취소를 다루는 Controller 테스트에서 따로 확인했습니다.[3][4]

### 남은 한계

DB 차원의 안전장치는 이번에 넣지 않았습니다. 회고에는 다음 버전(v1.1)에서 검토할 후보로 아이디어 하나만 남겨 뒀고, 구현 계획으로 확정한 것은 아닙니다.[3]

예약 행에는 지금 상태만 저장됩니다. `CANCELLED`라고 적혀 있으면 취소됐다는 건 알 수 있지만, 취소가 몇 번 처리됐는지는 알 수 없습니다. 그래서 `reservation_events` 테이블에 이벤트 이력을 남기고 `UNIQUE(reservation_id, event_type)` 제약을 걸어, 같은 예약에 같은 이벤트가 두 번 들어가지 못하게 하자는 아이디어였습니다. 아직 구현하지 않았고 채택 여부도 정하지 않았습니다.[3][4]

테스트는 H2에서 돌아갑니다. PostgreSQL에서 동시성을 검증한 결과로 볼 수는 없습니다.[4]

## 2. CodeRabbit 리뷰는 확인을 거쳐서 반영했습니다

### 사용 방식

처음에는 CodeRabbit 회원가입시 받은 설정을 그대로 사용했습니다. 그러다 GitHub에 push할 때마다 PR에 달리는 리뷰 코멘트가 작업 흐름을 끊어서 `auto_review: false`로 바꾸고 `review-ready` 라벨을 붙였을 때만 리뷰를 요청하도록 했습니다.[3]

10월 1일에 저장소별 설정 파일인 `.coderabbit.yaml`을 추가한 뒤 자동 리뷰를 꺼 둔 상태에서 라벨을 붙이면 리뷰가 생성되는 것을 재확인하였습니다. [4]

### 반영 기준

리뷰가 오면 두 가지를 따로 봤습니다. 하나는 제안된 diff가 현재 코드에 실제로 변화를 주는지, 다른 하나는 지적한 문제가 코드에 정말 있는지입니다. 이미 반영된 내용과 같은 제안은 적용하지 않았습니다.

- `updateSubspace`가 오래된 상태로 soft-delete를 덮어쓸 수 있다는 지적은 PR #35에서 고친 것으로 치지 않고 이슈 #47로 분리했습니다. #47은 아직 열려 있고, 수정도 회귀 검증도 끝나지 않았습니다.[3][4]
- 예약이 있는지 확인하는 조회가 `List<Reservation>`을 돌려주던 것을 `existsCurrentReservations`로 바꿔 Boolean을 돌려주게 했습니다. 메서드가 하는 일에 맞게 반환 타입을 고친 것이고, 성능을 재서 개선을 확인한 것은 아닙니다.[4]

## 3. 테스트 설정을 확인하고 CI 계획을 고쳤습니다

처음 CI 계획에서는 PostgreSQL 서비스를 띄우고 `rent-a-space.sql`로 초기화할 생각이었습니다. 그런데 회고에서 테스트 프로필을 먼저 확인해 봐야 한다는 메모를 남겼고, 실제로 보니 `application-test`는 H2 인메모리(`MODE=PostgreSQL`, `ddl-auto: create-drop`)를 쓰고 있었습니다. 그래서 GitHub Actions에 PostgreSQL을 추가하지 않고, Java 17과 Gradle Wrapper로 `./gradlew build`만 실행하도록 정리했습니다.[3][4]

10월 3일 기준, CI 실행 11건 중 CI 설정 중 실패 1건을 제외한 10건이 통과했습니다.[4]

### 검증하지 못한 부분

- `MODE=PostgreSQL`은 H2의 호환 모드일 뿐이고, 실제 PostgreSQL 서버에서 돌린 것이 아닙니다.
- 예약이 겹치지 않도록 막는 PostgreSQL 제약(`EXCLUDE USING gist`)은 `rent-a-space.sql`에 정의돼 있지만, H2 기반 CI로는 검증되지 않습니다. 이 내용은 README의 '알려진 제한'에도 적어 두었습니다.[4]
- 빌드가 통과했다고 해서 PostgreSQL 전용 제약이 동작한다거나, 운영에 배포할 수 있다거나, 부하를 견딘다는 근거가 되지는 않습니다.
- CI가 실패했을 때 브랜치 보호 규칙과 필수 체크가 실제로 머지를 막는지 아직 확인하지 않았습니다.[4]

## 현재 상태 요약

- **#36 취소 거부 처리:** 예외는 `IllegalStateException` 하나로 처리합니다. 이미 취소된 경우는 메시지(`"Reservation already cancelled"`)와 HTTP 409로 구분하고, 동시 요청은 비관적 락으로 막습니다.
- **#47 soft-delete 덮어쓰기:** 아직 해결하지 못했습니다.
- **테스트 프로필과 CI:** `src/test/resources/application-test.yml`을 사용합니다. CI는 `./gradlew build`로 H2 기반 테스트 11건을 실행했고 모두 통과했습니다.
- **PostgreSQL 전용 제약:** 정의만 되어 있고 검증하지 않았습니다.
- **브랜치 보호 설정:** 확인하지 않았습니다.
- **결제·정산:** MVP에서는 제외했고, 이후에 넣을지는 정하지 않았습니다.[1]
